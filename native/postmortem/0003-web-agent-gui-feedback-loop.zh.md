# 事故復盤（postmortem） 0003：Web agent（智能體）驗收了替代服務器，而非其當前 GUI

[English](0003-web-agent-gui-feedback-loop.md) | 中文

狀態：已解決

## 摘要

Web agent 修改了 GUI 源碼，卻不知道當前會話對應哪個 URL、由哪個進程承載。它把驗收交還給用戶，隨后在 `window.__DSH_BOOT__` 缺失導致白屏的情況下，仍把裸 Vite 返回的 HTTP 200 當作成功；最后，原頁面其實已經加載了重建產物，它卻去驗收另一個端口上的替代 `dsh web` 服務器。修復讓當前 URL 和運行模式對模型可見且可由 shell 查詢，在獨立 Vite 開始監聽前拒絕啟動，并依據外部狀態驗收生產模式刷新與開發模式 HMR（熱模塊替換）。

## 概述

該會話運行在端口 3081 的 DeepSeek Harness Web GUI 中，而用戶選擇的 Workspace 是空的 `test/` 目錄。模型請求既未指明該 GUI，也未提供它的源碼檢出目錄、URL、進程或更新模式。倉庫在 `apps/web` 中提供了 Vite 開發腳本，完整的瀏覽器組合則由 `dsh web` 提供。

由此產生的各個動作單看都合理，卻沒有指向同一個驗收目標。源碼修改、成功構建、HTTP 200、注入的啟動 manifest（元數據清單）和用戶原本打開的頁面，被當成了可以相互替代的事實。

證據源是 `session-3eb796c2-5159-4686-affe-df8719f6f987` 的持久化事件日志，其頭部記錄的 cwd 為 `/Users/tn.shen/Documents/deepseek-harness-gui-master/test`。初始請求頭位于序列 6；面向用戶的交接、裸 Vite 啟動、替代宿主啟動、啟動 manifest 探測，以及首次探測 3081 進程，分別位于序列 30939、31865、34309、34441 和 34681。下方時間線以這些事件為依據，而不是根據后續報告反推意圖。

## 影響

用戶不得不連續指出三個錯誤：agent 把驗收交還給用戶；建議預覽的頁面一片空白；報告成功的 URL 并不是用戶正在使用的頁面。一個不受管理的替代服務器還持續運行到下一個輪次，直到用戶提出質疑。

本次調查沒有重啟或修改只讀的 3081 和 3082 試驗服務。

## 時間線

- 在第 2 個輪次中，agent 修改主題后，在序列 30939 的消息中讓用戶運行 `pnpm run demo:tui` 或打開一個未明確指定的 Web 應用。它沒有對組裝后的 Web 應用執行任何驗收。
- 在第 3 個輪次中，agent 讀取 `apps/web/package.json`，在序列 31865 于端口 5173 上啟動裸 Vite，觀察到 HTTP 200 后便宣布成功。瀏覽器卻拋出 `client-modules: window.__DSH_BOOT__ is missing or not an object`，并顯示白屏。
- 在第 4 個輪次中，agent 找到了完整的 `dsh web` 啟動路徑，重新構建 shell，在序列 34309 于端口 3334 上啟動一個不受管理的進程，并且只在序列 34441 檢查了這個替代服務是否返回 200 和啟動 manifest。它從未探測端口 3081。
- 在第 5 個輪次中，用戶在序列 34556 報告 3081 已經顯示新主題。直到序列 34681，agent 才檢查既有進程并移除冗余服務器。

## 根因

Web 組合沒有向模型提供當前 GUI、規范 URL 或運行模式的身份信息。會話 cwd 正確標識了用戶選擇的 Workspace，但模型把這個項目目錄當成了應用目錄。系統也沒有持久記錄將 GUI 源碼檢出目錄、構建產物、服務進程、目標 origin 和瀏覽器驗收關聯起來。

裸 Vite 返回 HTTP 200，使錯誤的啟動路徑看似合理。`window.__DSH_BOOT__` 只由完整宿主注入，因此傳輸層就緒不代表應用已就緒。首個回歸測試以另一種方式重復了同樣的錯誤：超時機制終止 Vite 后，非零退出斷言仍會通過。真實復現暴露了這一誤報。

agent 還通過 shell `&` 繞過了后臺進程語義，因此任務身份、完成通知、結果收集和清理機制均未生效。驗證端口 3334 只能證明第二個服務可以工作。

## 已添加的防護措施

- Web 啟動器在記錄到日志的 `app:web-surface` 提示詞區段和受管的 `$DSH_WEB_URL` 環境變量中發布規范環回 URL。
- 生產指南要求重新構建產物，并在刷新后驗證既有 URL。開發指南說明 HMR 接收端始終開啟；同一源碼檢出目錄中的 `pnpm run dev:web` 會重新構建客戶端插件 bundle，實現免刷新的重載，而 Web shell 和普通包的改動仍然需要刷新頁面。
- `apps/web` 的獨立 Vite 服務模式會在配置階段拒絕啟動。其子進程測試驗證進程自然退出，并插樁 `Server.listen()`，確保短暫綁定端口也不會漏檢。
- 分層的真實路徑測試覆蓋 CLI（命令行界面）請求、精確的生產／開發模式提示詞、shell 運行時事實、同端口靜態產物替換、源碼 watcher 重建、宿主 stat 輪詢，以及頁面 identity 不變的瀏覽器 HMR。
- PR（Pull Request）證據保留了原始 3081 會話的截圖，以及真實模型驅動的 GUI 修改前后對比；驗收以外部瀏覽器、HTTP、進程和會話日志的觀測結果為準。

## 教訓

- agent 必須先知道隱藏的運行時前置條件，才能指導用戶；啟動模式屬于應用上下文，不應依賴團隊口口相傳。
- HTTP 就緒、構建成功和啟動 manifest 是不同的事實。驗收必須明確指定確切的 origin，并從外部觀察所請求的改動是否在該 origin 生效。
- 替代服務無法證明既有頁面已經改變。確實收到啟動長時間運行進程的請求時，應使用受管任務生命周期。
- 回歸測試必須能夠針對所報告的機制失敗。進程超時不等同于快速失敗，進程退出后端口可用也不能證明該端口從未被綁定。
