# 防御性模式

[English](defensive-patterns.md) | 中文

來之不易的缺陷類別規則：下面每條模式都是本項目實際發布或差點發布的一類缺陷，以防止其復發的規則形式陳述。在編寫生命周期、并發、子進程或清理代碼之前請先閱讀本文。測試層面的對應規則（真實入口路徑、驗證實際結果、資源歸屬）見 [testing.md](testing.zh.md)。

## 正交結果獨立上報

一個結果可以同時具有多種性質：進程可能已經超時，卻仍以退出碼 0 結束，因為它捕獲了終止信號。每個獨立事實（`timedOut`、`signal`、`exitCode`）都應單獨上報；切勿把一個標志的上報嵌套在另一個標志的分支中，否則調用方可能把提前終止的運行誤判為正常成功。

## 公共約定兩側都要遵守

當一個實現收到同一結果的多種表示時，應在通過公共 API 返回前將其規范化。`LlmAdapter.stream()` 的實現可以拋出異常或發出 `finish {kind:'error'|'aborted'}`，但 `LlmRuntime.stream()` 只會通過終止型 finish 分片暴露模型請求失敗；middleware 缺陷與消費方缺陷仍會以異常形式拋出。這使消費方不必猜測捕獲的異常究竟來自提供方、包裝層、分片日志記錄還是自身組裝邏輯。請在類型定義處記錄規范化后的約定；通過真實消費方覆蓋每種來源形式。

## 異步狀態不是同步狀態

`agent.followup()` 沒有逐消息的完成狀態或結果；后臺任務的完成與輪次邊界存在競爭；`reader.close()` 在 EOF 和 dispose（資源釋放）兩種情況下都會觸發。切勿把 `agent/status` 或 `whenIdle()` 當作某次 `followup()` 的結果：多條已排隊的后續消息、steering（中途引導）和注入工作可能共用同一個 `running` 區間，而取消或資源釋放可能丟棄尚未啟動的項。真正擁有一次運行的自動化調用方必須顯式定義其區間——例如從消息的持久 inbox 回執到整個 agent（智能體）下一次進入 `idle`——并將選取的任何輸出描述為整個區間的輸出，而不是把因果關系歸于該消息。這條守則是雙向的：如果等待的轉換永遠不會發生，等待就會掛起，因此應顯式處理「無需等待」的分支。

<a id="dispose-must-reach-quiescence-not-just-request-it"></a>

## dispose 必須達到完全停穩，而不僅僅是請求停止

如果清理流程只發出終止或中止信號便返回，而不等待工作真正停止，就會留下孤兒進程。清理邏輯應采用異步流程，并等待子進程退出（發出終止信號后等待 `done`）；還應在終止進程前關閉監聽器注冊表和通知注冊表，使遲到的完成事件保持靜默。

## 在分發器中隔離回調異常

用戶提供的監聽器如果拋出異常，不得導致它所在的 promise 被 reject，也不得餓死排在它后面的監聽器。請用 try/catch 包裹分發循環并記錄日志；一個行為不當的訂閱者絕不能破壞核心生命周期。

## 絕不將環境變量或可預測路徑暴露給不可信輸出

啟動的命令應使用經過清理的環境變量，移除名稱匹配 `*KEY*`、`*SECRET*`、`*TOKEN*` 或 `*PASSWORD*` 的項，防止 harness 憑證通過命令輸出、`env` 或 spill 文件泄漏。臨時文件和 spill 文件應放在權限為 0700 的私有目錄中，使用隨機文件名，并以獨占且僅所有者可訪問的方式打開（`'wx'`、`0o600`）；可預測且全局可讀的路徑會引發符號鏈接競態和信息泄露。

## 用 unlink 刪除鏈接形態的路徑

可能是符號鏈接或 Windows junction 的路徑，應先用 `lstatSync().isSymbolicLink()` 判斷，再用 `unlinkSync` 刪除：unlink 只刪除鏈接本身并拒絕真實目錄，因此絕不會跟隨鏈接進入其目標。Windows 上對 junction 調用 `rmSync(link)` 會拋 `ERR_FS_EISDIR`；遞歸刪除可能穿過 junction 進入其目標。真實目錄才使用帶 `recursive` 的 `rmSync`。
