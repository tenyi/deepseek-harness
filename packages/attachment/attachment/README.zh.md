# @deepseek-ai/dsh-attachment

[English](README.md) | 中文

## 概述

把圖片與通用文件附加到提示詞和命令中，同一會話重啟后仍可復用；隨附的 `dsh` 組合無需額外配置。圖片會在消息被接受前完成校驗與規范化；部署限額內支持 PNG、JPEG、WebP 和 GIF。其他文件按字節原樣保存，不設格式與大小限制；模型通過保存的只讀路徑按需讀取，而不接收文件字節。持久會話事件不包含瀏覽器路徑、提供方 URL、本地存儲路徑和 base64。已存儲附件不會被自動刪除；音頻和視頻暫無專門處理。

<a id="use-this-package"></a>
## 使用本包

圖片附件端到端可用：把圖片附加到提示詞或命令，它會自動保存、顯示在歷史中并發送給模型，無需你再做任何操作。在默認 `dsh` 組合中一切都已接好；自行組合時，一個插件即可啟用該能力。

### 在提示詞中附加圖片

在客戶端 UI 中向用戶提示詞附加一張或多張圖片。每個源圖都會在你的消息被處理前接受檢查、規范化為提供方無關的 8-bit sRGB/sRGBA 光柵并保存；如果任何一張圖片被拒絕，整條消息都會失敗且不會發布任何內容。支持的源格式為 PNG、JPEG、WebP 與 GIF；部署方分別控制源圖限制、規范化存儲限制與路由專用請求限制。下面這一個插件即可啟用持久圖片附件（隨附的 base 組合已經掛載它）：

```yaml
- name: '@deepseek-ai/dsh-attachment-local'
```

### 在提示詞中附加任意其他文件

任何非圖片文件都以通用文件的形式附加到提示詞：確切字節被只讀保存在 harness 主目錄下，消息記錄文件名、字節數與內容摘要，模型收到一行指出保存路徑的文本，只在需要時用文件工具讀取內容。沒有文件類型白名單，也沒有大小上限；你附加什么就原樣存什么。

### 把附件傳給命令

聲明接受附件的命令會按選擇順序接收圖片與通用文件。不接受附件的命令會返回錯誤，并保留輸入區的草稿與附件卡。

### 在整個會話中復用圖片

已保存的規范化圖片會保留在對話歷史中，并在后續輪次投影為確定性的路由尺寸請求版本；重啟后，恢復的會話會顯示并復用相同的圖片。當前執行文件系統可以映射已存宿主對象時，請求描述符還會攜帶模型可檢查的只讀進程路徑。回讀歷史或請求版本時，已存儲的字節會與記錄的內容比對，因此缺失、損壞或被替換的圖片會以錯誤形式呈現，而不是錯誤的字節。

### 可能出什么問題

附加圖片時可能被拒絕——格式不受支持、超出大小、像素或尺寸限制，或者字節與聲明類型不符——此時整條消息失敗。之后，如果磁盤上的圖片被刪除或損壞，歷史讀取也可能失敗。失敗帶有穩定錯誤碼，客戶端與協議適配器可以用自己的措辭解釋它們。

<a id="understand-the-implementation"></a>
## 理解實現

<details>
<summary>實現細節——點擊展開</summary>

本節解釋 seam 背后的設計決策，以及實現用戶可見行為的服務操作；可觀察行為已在[使用本包](#use-this-package)中完整說明。

### 設計決策

- **事件前完成規范化與持久化。** 每個源圖都會在批次按序發布前完成準備與校驗，因此會話日志絕不會引用部分完成或規范化失敗的對象。
- **不可變且保留策略中立。** 對象一經發布即不可變；恢復和 fork 后的會話可能共享它們，因此引用感知的垃圾回收被推遲，而不是與任何單個會話的刪除綁定。
- **讀取時校驗。** 讀取在返回前把字節和元數據與記錄的引用比對，請求投影還會完整解碼緩存字節，因此缺失、損壞或被替換的對象不會通過校驗。
- **角色無關的圖片塊。** `dsh-llm` 中的 `ImageBlock` 內容塊攜帶 `ImageAttachmentRef`；提供方適配器以顯式像素與字節預算把引用解析為確定性請求版本，執行文件系統則可以把不可變宿主對象映射為模型可讀的進程路徑。
- **按錯誤碼路由。** `AttachmentError` 重新實現 `HarnessError` 的結構而不是繼承它，因為基類位于 `dsh-llm`，而后者依賴本包；消費方用 `isAttachmentError` 識別錯誤并按 `code` 路由，絕不依賴原型鏈。
- **文件原樣，圖片規范化。**`saveFile` 提交已有字節數組，`saveFileStream` 以背壓和取消語義提交有界分塊，`readFileStream` 校驗并返回有界分塊，`fileHostPath` 定位存儲對象供按需讀取投影；兩種文件寫入路徑都不設準入限制。圖片路徑保留其獨立的規范化、限額與請求版本流水線。`dsh-llm` 中的 `FileBlock` 內容塊承載 `FileAttachmentRef`，請求組裝會為每條路由將其投影為確定性的句柄文本。

### 服務操作

服務族運行同一條準入與存儲流程：每個入口都強制執行源批次限制與規范 base64，在發布任何成員前準備提供方無關的規范化附件，再按輸入順序持久提交而不產生部分結果。Host 提示詞消費方把有序文本、編碼圖片和已經解析的文件引用交給 `ctx.attachments.admitPromptContent()`；該方法持久化圖片，并讓文件引用原樣通過。編碼協議適配器調用 `ctx.attachments.admitEncodedFile()`，由該方法檢查規范 base64 后委托給 `saveFile`；適配器通過 `ctx.attachments.isAttachmentError()` 識別附件錯誤。通用文件調用方可以用 `saveFile` 提交已有字節，或用 `saveFileStream` 提交有界異步字節源；兩者返回相同的持久引用，`readFileStream` 則在有界讀取過程中校驗摘要與長度。`readImageRequest` 派生確定性的路由尺寸變體，其身份包含附件 id、變換版本、像素與字節預算及編碼參數。純函數導出 `requestImageDimensions` 會按總像素預算計算每個投影保持寬高比的尺寸，使提供方與請求定價共享同一套幾何計算。`imageHostPath` 只向需要把該位置映射到執行環境的受信任同進程消費方暴露實現擁有的宿主位置。調用方組合有序批次，而實現負責管理壓縮并發、緩存與 singleflight。讀取、流式寫入和投影保留調用方的取消語義。失敗帶有穩定且機器可讀的錯誤碼，運行時即可識別可由調用方修正的準入子集，讓每個協議適配器映射自己的詞匯；各操作的確切約定見 [`src/index.ts`](src/index.ts) 與 [`src/error.ts`](src/error.ts)。

<a id="model-experience"></a>
## 模型體驗

該包通過提供方適配器間接影響模型；適配器會把每個持久圖片引用解析為確切請求版本，并在圖片旁發送穩定附件 id 與實際尺寸。執行文件系統可以映射已存對象時，描述符還會包含只讀進程路徑，以及可寫副本使用的匹配擴展名。通用文件的字節永遠不會到達提供方：每條路由都收到一行確定性的句柄文本，指出文件名、字節數、摘要前綴，以及供文件工具讀取的只讀保存路徑。

#### KV Cache 影響

添加圖片會改變提供方請求，因此會使受影響的請求后綴失效。

## 已知限制與延期工作

<a id="known-limitations-and-deferred-work"></a>


這些限制描述了附件能做什么、不能做什么；它們是當前包約束，而非任務積壓。

- **光柵圖片限制只作用于圖片**——圖片接受部署限額內的 PNG、JPEG、WebP 與 GIF；其他任何文件都原樣保存、不設類型與大小限制，音頻和視頻暫無專門處理。
- **附件永遠不會被刪除**——已存儲的圖片與文件無限期保留；沒有任何機制自動移除它們。
- **未發送的草稿不會保存**——輸入區草稿在提交消息前一直留在瀏覽器中。
